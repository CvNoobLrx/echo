# 01｜先看懂 HappyBull 的 RAG 全貌

## 这一篇要解决的问题

这篇先回答三个问题：项目里的 RAG 从哪里开始，数据经过哪些阶段，聊天时又从哪里被取出来。读完后，你应该能拿着一条用户问题，在源码中完整指出它的入库路线和检索路线。

## 正文

### 1. 先给这套 RAG 一句定义

HappyBull 的知识库 RAG 是一套“结构化解析 + 父子分块 + Elasticsearch 混合检索 + 可选 Rerank + Agent 工具调用”的系统。

它有两条主要流水线：

```text
入库链
上传文件
  → 保存原文件和文档元数据
  → Celery 后台解析
  → 生成结构化 Block
  → 生成 Parent / Child Chunk
  → Child 向量化
  → Parent 与 Child 写入 Elasticsearch

查询链
用户问题
  → Agent 决定调用 knowledge_search
  → 问题向量化
  → 向量 KNN + BM25 召回 Child
  → 0.6 / 0.4 融合
  → 可选 Rerank
  → 根据 parent_id 取回 Parent
  → Parent 内容交给模型生成回答
  → 收集文档引用
```

整套链路的核心目录是 `api/app/core/rag/`，外围入口分散在 service、后台任务和 Agent 工具中。

### 2. RAG 代码地图

先记住下面这组文件。此时只需知道职责，无须逐行阅读。

| 阶段 | 核心文件 | 职责 |
|---|---|---|
| 上传入口 | `api/app/services/document_service.py` | 校验文件、保存原文件、创建文档记录、派发解析任务 |
| 后台编排 | `api/app/tasks/parse.py` | 串联读取、解析、分块、Embedding、写索引和自动标签 |
| 解析流水线 | `api/app/core/rag/ingestion/pipeline.py` | 文件体检、解析器选择、失败回退、规范化、质量判断 |
| 中间结构 | `api/app/core/rag/ingestion/models.py` | 定义 DocumentProfile、DocumentBlock、ParsedDocument |
| 解析器路由 | `api/app/core/rag/ingestion/router.py` | 普通 PDF、复杂 PDF、文本类文件的解析器选择 |
| 父子分块 | `api/app/core/rag/chunking/block_chunker.py` | 按标题、Block 类型和 token 上限构造 Parent / Child |
| ES 映射 | `api/app/core/rag/indexing/es_index.py` | 定义 `echo_chunks` 的字段、中文分词和 1024 维向量 |
| ES 写入 | `api/app/core/rag/indexing/es_store.py` | 构造、批量写入、删除和更新 Chunk |
| 混合检索 | `api/app/core/rag/retrieval/search.py` | KNN、BM25、融合、Rerank、父块回填和检索 Trace |
| Agent 工具 | `api/app/core/agent/tools/builtin/knowledge.py` | 把检索包装为 `knowledge_search`，并收集引用 |
| 对话范围 | `api/app/services/chat_service.py` | 决定本轮是否启用知识库工具，以及允许搜索哪些知识库 |
| 验证界面 | `web/src/pages/KnowledgeDetailPage.tsx` | 展示各阶段分数、Child、Parent 和原始 Block |

推荐的源码阅读顺序是：`parse.py` → `block_chunker.py` → `search.py` → `knowledge.py`。这个顺序贴近数据流，阅读时容易形成因果关系。

### 3. 一份文档怎样进入知识库

上传请求进入 `DocumentService.upload()` 后，会发生四件事：

1. 校验扩展名和 50 MB 大小限制。
2. 把原文件放到对象存储。
3. 在 PostgreSQL 的 `documents` 表建立一条 `pending` 记录。
4. 向 Celery 派发 `parse_document_task`。

后台任务位于 `api/app/tasks/parse.py`。它是入库链的总导演，步骤在源码中已经用注释编号：

```text
对象存储取文件
  → parse_document_structured()
  → document_blocks 表
  → chunk_blocks()
  → Embedding 客户端
  → delete_by_source()
  → bulk_index()
  → 可选的自动标签
```

这里有三个不同粒度的数据对象：

| 数据层 | 大致粒度 | 保存位置 | 主要用途 |
|---|---:|---|---|
| DocumentBlock | 标题、段落、列表、表格等自然结构 | PostgreSQL `document_blocks` | 保留页码、标题路径和原始结构，支持追溯与验证 |
| Parent Chunk | 最多约 1024 token | Elasticsearch | 给大模型提供完整上下文 |
| Child Chunk | 约 256 token，10% 重叠 | Elasticsearch | 做向量和关键词召回 |

Parent 与 Child 的配合很关键。短 Child 更容易精确匹配问题，长 Parent 能提供回答所需的上下文。系统只给 Child 计算向量；Parent 的 `vector` 为 `None`。Child 通过 `parent_id` 指向 Parent。

举个缩小后的例子：

```text
Parent：第三章 售后规则
  退货期限为签收后 7 天。定制商品不支持无理由退货。
  退款将在审核通过后 3 个工作日内原路退回。

Child A：退货期限为签收后 7 天。定制商品不支持无理由退货。
Child B：退款将在审核通过后 3 个工作日内原路退回。
```

用户问“退款多久到账”时，Child B 更容易被命中。命中后系统沿 `parent_id` 取回整个 Parent，让模型同时看到章节主题和相邻规则。

### 4. 解析器怎样选择

`parse_document_structured()` 先让 `FileInspector` 检查文件，再让 `ParserRouter` 选择解析器。

文本类文件的路线比较直接：

- `.txt`、`.md`、`.markdown`、`.html`、`.htm`、`.docx` 使用 `PlainParser`。
- 普通 PDF 使用 `PyMuPDFParser`。
- 扫描风险、多栏或图片密集的复杂 PDF，在配置开启且运行环境可用时使用 `DoclingParser`。
- Docling 执行失败时回退到 PyMuPDF，并把回退原因写入解析告警。

解析器最终都返回统一的 `ParsedDocument`。其中每个 `DocumentBlock` 可以携带 `block_type`、页码、标题路径和额外元数据。后面的分块器只依赖这套统一结构，因此解析实现可以继续扩展，而检索链保持稳定。

### 5. 父子分块怎样工作

`chunk_blocks()` 的几个规则值得先记住：

1. Parent 上限是 1024 token，Child 目标是 256 token。
2. 标题路径变化时结束当前 Parent。
3. 表格单独成组，避免表格与周围段落混切。
4. 超长 Block 使用 token 窗口切分。
5. 普通 Child 尽量沿句号、问号、感叹号和换行边界切分。
6. Child 保留约 10% 重叠，降低答案横跨边界时的漏召回概率。

Parent 和 Child 都继承关联 Block 的页码、类型与标题路径。检索结果因此可以回答“命中了哪一页、哪个标题下、哪类原始结构”，这也解释了前端检索验证页为什么能展开原始 Block。

### 6. 一次查询怎样完成混合检索

核心入口是 `hybrid_search()`，实际算法集中在 `_run_hybrid_search()`。

第一步是确定检索范围：

- 始终过滤 `user_id`，保证用户隔离。
- 根据场景过滤 Child 文档块或图片描述块。
- 按需过滤 `kb_id`、标签和来源类型。
- 对话场景通常只搜索开启了“聊天检索”的知识库；绑定知识库的 Skill 会把范围缩到该库。

第二步产生两组候选：

- 向量支路：把问题变成 Embedding，在 `vector` 字段做 KNN，默认召回 20 条，ES 内部候选数是 100。
- 关键词支路：对 `content` 做 BM25。索引使用 `ik_max_word`，查询使用 `ik_smart`。

第三步融合分数。向量分和 BM25 分的量纲不同，代码先分别做 min-max 归一化，再计算：

```text
fusion = 0.6 × vector_normalized + 0.4 × bm25_normalized
```

如果用户配置了 Rerank 模型，融合候选会继续交给 Rerank 排序。Rerank 调用失败时，系统保留融合排序，并把错误写入 Trace。

最后，检索器拿每个 Child 的 `parent_id` 查询 Parent 内容。业务返回值里：

- `matched_content` 是实际命中的 Child。
- `content` 是交给回答侧使用的 Parent。
- `page_start`、`heading_path` 等字段用于定位来源。

### 7. 检索怎样进入聊天回答

`api/app/core/agent/tools/builtin/knowledge.py` 注册了一个默认启用的 `knowledge_search` 工具。工具说明告诉模型：当问题涉及用户上传的资料、文档或笔记时，可以调用它。

这意味着聊天流程中仍有一层 Agent 决策：模型根据问题和工具描述决定是否发起检索。调用后，工具固定取 Top 5，把每条命中的 Parent 拼成“检索到以下知识库内容”，再交回模型生成自然语言答案。

引用的生成方式也很直接：工具从命中结果中读取 `source_id`、`source_type`、`doc_name` 和 `score`，按 `source_id` 去重后写入本轮引用收集器。

知识库范围由 `ChatService._tool_scope()` 决定：

- 对话页的临时开关可以关闭或开启知识库工具。
- Skill 有绑定知识库时，只传入该知识库 ID。
- 普通对话读取用户所有 `chat_enabled` 的知识库 ID。
- 可用知识库列表为空时，检索器直接返回空结果，不访问 ES。

### 8. 这套设计最值得学习的地方

第一，系统保留了三层数据。Block 负责结构与追溯，Child 负责精准召回，Parent 负责上下文。这种职责分工比单一固定长度 Chunk 更容易调试。

第二，入库链通过统一中间模型隔离了解析器差异。Docling、PyMuPDF 和 PlainParser 的输出最终都变成 `DocumentBlock`。

第三，检索过程具有可解释 Trace。项目的知识库详情页可以同时显示向量分、BM25 分、融合分、Rerank 分、各阶段排名、Child、Parent 和原始 Block。

第四，降级路径比较完整。复杂 PDF 可以回退，Rerank 失败可以回退，Parent 丢失时可以退回 Child 内容。

### 9. 阅读源码时先留意的四个细节

这些细节会在后续文章展开：

1. 融合前的 min-max 归一化是“本次候选集合内的相对分数”，不同查询的融合分不适合直接横向比较。
2. 多个 Child 可能指向同一个 Parent，当前检索返回阶段没有按 Parent 去重，回答上下文可能出现重复。
3. `_resolve_parent()` 会对每条最终命中再查一次 ES，Top K 较大时形成额外查询次数。
4. Rerank 改变最终顺序后，结果顶层的 `score` 仍取融合分；Rerank 分单独保存在 `scores.rerank_score`。

这些属于理解实现边界的观察点，不影响你先掌握主流程。

### 10. 现在可以怎样动手验证

无需先写代码。启动项目并准备好 Chat、Embedding 模型后，可以完成一次最小实验：

1. 新建知识库并打开聊天检索。
2. 上传一份带标题、正文和表格的小文档。
3. 等文档状态变为完成，观察解析器、Parent 数和 Child 数。
4. 进入知识库详情的检索验证页，输入一个语义问题。
5. 依次展开命中 Child、Parent 上下文和原始 Block。
6. 换成文档原词再次搜索，比较向量排名与 BM25 排名。
7. 回到聊天页问相同问题，观察 Agent 是否调用知识库工具并产生引用。

这个实验能把源码中的对象映射到界面中的可见结果。

## 小结

1. HappyBull 的 RAG 分为文档入库链和查询回答链，两条链在 Elasticsearch 的 Child / Parent 数据处连接。
2. Block 保存结构与来源，Child 用于精确召回，Parent 用于提供回答上下文。
3. 查询采用向量 KNN 与 BM25 双路召回，归一化后按 0.6 / 0.4 融合，并支持可选 Rerank。
4. `knowledge_search` 把检索能力交给 Agent，知识库范围由对话设置或 Skill 绑定关系控制。
5. 检索验证页是学习和排错的最佳入口，它能把分数、排名与三层文本同时展示出来。
